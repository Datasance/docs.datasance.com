The **<ProductName />** architecture has several building blocks. Together they form a logical cluster called an **Edge Compute Network (ECN)**.

## Core principles

**<ProductName />** gives you one control point to deploy, operate, and govern container workloads across large edge environments. It brings cloud-native operating principles to the edge. You focus on applications instead of infrastructure, security, and networking.

The platform is designed around three principles:

- **Distributed**, to preserve local autonomy and resilience
- **Disaggregated**, to stay independent of hardware, operating systems, and environments
- **Control-centric**, with unified operations and security as first-class concerns

These principles let **<ProductName />** manage isolated edge sites as one coherent system without forcing central dependency.

## Control plane and Edgelet nodes

The **Control Plane** coordinates distributed edge environments from a central point. It is backend-agnostic. It runs on Kubernetes clusters, bare-metal hosts, or virtual machines.

An **Edgelet node** is the worker of an ECN. The same Edgelet binary is the node agent, the application runtime, and the container engine. You can also run that binary on a Linux host by itself, with the `edgelet` CLI, before any control plane exists. Joining a cluster later uses <CliName /> and `kind: Agent`.

Edgelet is built for small, mixed edge hardware.

- On Linux the OTA download is the thin binary, less than **35 MB**. It is the CLI and the update artifact. The container engine is packed inside that file.
- Linux builds ship for **amd64**, **arm64**, **arm** (32-bit, including armv7), and **riscv64**. The YAML key for 32-bit ARM is `arm`.
- The default container engine is embedded. A host does not need Docker or Podman to run containerized workloads or AI applications. macOS and Windows use Docker or Podman.
- The engine stores registries, container images, **Model** weights, and **Knowledge** bundles. Built-in rows cover Docker Hub, a local image cache, and Hugging Face. Private OCI and Hugging Face rows are the same kind of object.
- Wasm workloads use a built-in RuntimeClass catalog, including the `edgelet-wasmtime` shim. A cluster install stages those shim binaries when `package.wasm` is set on the Agent. Wasm is a container on this engine, not a second runtime you install by hand.

Day-2 operations use the [Controller](#controller), [EdgeOps Console](#edgeops-console), or **<CliName />**. You deploy and maintain microservices without SSH on every edge device.

## Secure, scalable, hardware-agnostic

Security and control are built in from the start. The platform scales from a few sites to large, geographically distributed clusters. Its hardware-agnostic design lets you choose and evolve edge hardware while keeping consistent operational control across the environment.

Supported node architectures include **amd64**, **arm64**, **riscv64**, and **arm** (32-bit).

## Controller

The **Controller** (**v3.9.0**) is the heart of each ECN. It orchestrates Edgelet nodes, microservices, Router and NATS instances, RBAC, secrets, certificates, fleet **Model** and **Knowledge** catalogs, and more.

The Controller can run on bare-metal, virtual hardware, or Kubernetes. Every Edgelet node must reach it over the network. That usually means a static IP address or DNS records.

You can also place the Controller behind an HTTP ingress. The Controller is fully functional through its REST and WebSocket APIs.

The Controller image embeds **EdgeOps Console** (**v1.1.0**) on port **8008**. Default installs use [embedded OIDC](/get-started/deploy/embedded-oidc) for authentication.

On **v3.9.0**, the Controller catalog pulls AI **weights** and **knowledge** artifacts from **`type: oci`** and **`type: hf`** [registries](/learn/config/registries), tracks attach state per **Edgelet node**, and prepares mounts for microservices that bind **`spec.models`** and **`spec.knowledge`**. See [AI Model Catalog](/learn/config/ai-model-catalog) and [AI Knowledge Catalog](/learn/config/ai-knowledge-catalog).

## EdgeOps Console

**EdgeOps Console** is the web UI for **<ProductName />**. It is embedded in the Controller image. You manage Edgelet nodes, applications, microservices, routes, AI catalogs, and supporting resources from the browser.

## Edgelet nodes

An **Edgelet node** is the worker of an ECN. Each node runs the **Edgelet** runtime and hosts microservices, volumes, and local resources. Every Edgelet node reports to the Controller. The Controller must be reachable from edge nodes, but edge nodes do not need to be reachable from the Controller.

Edgelet manages microservices as containers. It handles their lifecycle and local container images. Edgelet supports multiple CPU architectures and container engines.

Day-2 operations use the [Controller](#controller), [EdgeOps Console](#edgeops-console), or **<CliName />**. You deploy and maintain microservices without SSH on every edge device.

## Microservices

Microservices are the workloads that run on Edgelet nodes. Each microservice is a Linux or Wasm container. Many microservices can run on one Edgelet node. This is similar to Kubernetes pods, except **<ProductName />** gives you granular control over which nodes run which microservices.

On **v3.9.0**, microservices can bind fleet **Model** and **Knowledge** catalog entries through **`spec.models`** and **`spec.knowledge`**, and use expanded **`container`** fields for production hardening. See [Microservices in Learn](/learn/workloads/microservices#specmodels-and-specknowledge).

## Router

The **Router** enables microservices to communicate through TCP bridges created via Service YAML kinds. The platform ships a Router wrapper image (**v3.9.0**) that embeds **Skupper Router 3.5.1**. Router is deployed with TLS by default. The Controller tracks Router configuration and TLS certificate volume mounts.

Each Controller and each Edgelet node has its own Router instance by default. The Controller hosts an **interior** Router. Each Edgelet node hosts an **edge** Router connected to the interior Router.

You can change the topology. For example, you can share edge Routers between nodes or run interior Routers on Edgelet nodes instead of the Controller.

<FlavorYaml title="Edge Router on an Edgelet node">{`---
apiVersion: {{API_VERSION}}
kind: Agent
metadata:
  name: foo
spec:
  ...
  config:
    ...
    upstreamRouter:
      - default-router
    routerConfig:
      routerMode: edge
      messagingPort: 5671
`}</FlavorYaml>

<FlavorYaml title="Interior Router on an Edgelet node">{`---
apiVersion: {{API_VERSION}}
kind: Agent
metadata:
  name: edge-2
spec:
  ...
  config:
    ...
    upstreamRouter:
      - default-router
    routerConfig:
      routerMode: interior
      messagingPort: 5671
      edgeRouterPort: 45671
      interRouterPort: 55671
`}</FlavorYaml>

<FlavorYaml title="Edge Router with two upstream interior Routers">{`---

## NATS

**NATS** is the default messaging infrastructure for **<ProductName />**. It provides pub/sub, request/reply, key-value storage, and JetStream. The platform ships a NATS wrapper image that pins upstream **NATS Server 2.15.0**. When enabled, NATS instances deploy with TLS by default.

The Controller tracks NATS configuration, TLS certificates, account JWTs, and creds. Applications and microservices get NATS access through **NATS Account Rules** (application level) and **NATS User Rules** (microservice level). The Controller provisions credentials so you do not manage JWTs and cred files manually.

Each Controller and each Edgelet node has its own NATS instance by default. The Controller runs NATS in **server** mode and forms a NATS cluster with all server-mode instances. Each Edgelet node runs NATS in **leaf** mode by default. Leaf nodes connect to upstream server-mode instances.

You can run NATS in **server** mode on an Edgelet node and add it to the NATS cluster.

<FlavorYaml title="Leaf NATS on an Edgelet node">{`---
apiVersion: {{API_VERSION}}
kind: Agent
metadata:
  name: foo
spec:
  ...
  config:
    ...
    upstreamNatsServer:
      - default-nats-hub
    natsConfig:
      natsMode: leaf
      natsServerPort: 4222
      natsLeafPort: 7422
      natsMqttPort: 8883
      natsHttpPort: 8222
      jsStorageSize: 10g
      jsMemoryStoreSize: 1g
`}</FlavorYaml>

<FlavorYaml title="Server NATS on an Edgelet node">{`---
apiVersion: {{API_VERSION}}
kind: Agent
metadata:
  name: edge-2
spec:
  ...
  config:
    ...
    natsConfig:
      natsMode: server
      natsServerPort: 4222
      natsLeafPort: 7422
      natsClusterPort: 6222
      natsMqttPort: 8883
      natsHttpPort: 8222
      jsStorageSize: 10g
      jsMemoryStoreSize: 1g
`}</FlavorYaml>

<FlavorYaml title="Leaf NATS with two upstream servers">{`---
apiVersion: {{API_VERSION}}
kind: Agent
metadata:
  name: foo
spec:
  ...
  config:
    ...
    upstreamNatsServer:
      - default-nats-hub
      - edge-2
    natsConfig:
      natsMode: leaf
      natsServerPort: 4222
      natsLeafPort: 7422
      natsMqttPort: 8883
      natsHttpPort: 8222
      jsStorageSize: 10g
      jsMemoryStoreSize: 1g

## Operator

The **Operator** (ioFog Operator **v3.9.0**) manages Kubernetes Custom Resources for **<ProductName />**. It reconciles Control Plane and related CRDs.

When you deploy **<ProductName />** on Kubernetes with **<CliName />** or Helm, the Operator is the first component installed in the namespace. When you create a Control Plane custom resource, the Operator deploys the ECN components in that namespace.
